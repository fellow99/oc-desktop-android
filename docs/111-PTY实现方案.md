> **版本**：v0.1（方案稿）｜ **日期**：2026-11-02

> **状态**：**方案评审中（未动工）** —— 本文件是「决策记录 + 分阶段实施规划」，不是已落地证据。

## 0. 一句话方案

利用已经上架到 Maven Central 的 **`io.github.fellow99:node-pty`（进程内 N-API addon，`libpty_node.so`）**，给 oc-desktop-android 的**进程内 Node**补上真正的 PTY 能力，从而点亮 opencode Web UI 的**终端面板**；采用**三个阶段递进**：

- **Phase 0 · Spike**：验证 node-pty 在进程内 Node 能加载、且能 `spawn("/system/bin/sh")`，同时**先禁用** Web UI 终端（PersistentPty），把「终端」从能力矩阵的 ❌ 拆成「Spike 前禁用的界面入口」；
- **Phase B · 首个里程碑**：升 Node 到 **26.13.0**（配 `node-pty:26.13.0`），实现**进程内 PersistentPty 最小可用后端**，让官方终端「能用」；快照 / read_rows / 跨重启持久化 等按能力**降级**；
- **Phase A · 递进**：补全快照 / 光标 / 跨重启 handoff 等，与官方桌面终端行为对齐。

> 目标设备仍以平板 / 折叠 / 桌面窗口优先；ABI 仅 **arm64-v8a**（`node-pty` 只发布该架构，与运行时 lock 一致）。

## 1. 背景：为什么「PTY」此前是平台级 ❌

能力清单（`docs/安卓环境能力清单-2.1.2.md`）把「终端 / PTY」列为 **D3 ❌**，根因（§4 L1）是：
**应用数据分区 noexec + 无法 spawn 外部原生 ELF** ⇒ opencode 原生的 `persistent-pty-binary`（一个独立守护 ELF）
在 Android 上拿不到，也无法作为子进程执行。

本次的**关键变化**是：`node-pty` 已经以 **进程内 N-API addon**（`libpty_node.so`，可被 dlopen 进进程内 Node）的形式上架，
**绕开了「spawn 外部 ELF」这个死结** —— 它和 `libnode.so` 一样，从只读 `nativeLibraryDir` 由本进程加载。
这是本方案成立的事实基础。

## 2. 现状溯源（代码证据）

以下结论均来自对 opencode v2.2.5 源码的实扫（非「应该是」），是方案的地基。

### 2.1 Web UI 终端用的是 `PersistentPty`（守护进程），不是进程内 `Pty`

| 层 | 文件 | 结论 |
|---|---|---|
| 前端 | `opencode/packages/gui-plugins/src/terminal/{connection,model}.ts` | 终端面板调用 `client.experimental.persistentPty.list/create/…`；可用性开关 `info.capabilities?.persistentPty !== false` |
| 服务端处理器 | `opencode/packages/server/src/handlers/persistent-pty.ts` | 把 `PersistentPty` 服务暴露为 HTTP/SSE 路由 |
| 核心服务 | `opencode/packages/core/src/persistent-pty/` | `index.ts` + `daemon.ts` + `pty-binding.ts` + `binary.{bun,node,workerd}.ts` |

### 2.2 原生的 `PersistentPty` 是「外部守护 ELF」

`opencode/packages/core/src/persistent-pty/daemon.ts`：

- `spawn(executable, ["daemon","--runtime-dir", root,"--name", id], { detached:true, stdio:"ignore" })`；
- executable 由 `#persistent-pty-binary` 解析 → `OPENCODE_PTY_BIN` 或 PATH 上的 **`opencode-pty`**（独立 ELF）；
- 守护**注册**：写 `<state>/pty/<id>/service.json`；**通信**：Unix socket + 「4 字节长度前缀 + JSON 帧」协议；
- 守护内部用一个原生 PTY 库维护**屏幕状态 / snapshot / checkpoint 回放 / read_rows / 光标 / 跨重启 handoff**。

**这正是 Android L1 卡死的点**：该 ELF 无法在 Android 上以子进程运行。

### 2.3 进程内 `Pty` 服务已经预留了 node-pty 钩子

`opencode/packages/core/src/pty/pty.node.ts`：

```ts
const pty = createRequire(import.meta.url)(process.env.OPENCODE_NODE_PTY_PATH ?? "@lydell/node-pty")
```

即进程内 `Pty` 服务**本就走 node-pty 绑定**，只是 GUI 终端没走它（它语义更简：attach/replay/write/onEnd，无快照、无跨重启）。
这条钩子（`OPENCODE_NODE_PTY_PATH`）是**可选捷径**，Phase A 可复用于对齐，但**不是**灯亮终端面板的必要路径。

### 2.4 node-pty AAR 的加载契约（aosp-node-pty README 实测）

`io.github.fellow99:node-pty:<node>` AAR 内**只有** `jni/arm64-v8a/libpty_node.so`（N-API addon，`DT_NEEDED libnode.so`，无 JS wrapper）：

- 与 `node-runtime:<node>` **必须逐字同版本**（`NODE_MODULE_VERSION` 不一致即不可用；26.13.0 = ABI 147）；
- 加载方式：`System.loadLibrary("pty_node")` 预载，**或**在 Node 侧把 node-pty 的 addon 解析覆盖到 `<nativeLibraryDir>/libpty_node.so` 的绝对路径；
- 绑定可用性由 `forkpty/openpty` 提供，bionic 已在 libc 内置（无需 `-lutil`）。

## 4. 总体架构（分阶段）

```
                          +-------------------------------+
                          |       进程内 Node (26.13.0)      |
                          |                               |
   Web UI 终端面板          |   PersistentPty 服务 (core)      |
   (gui-plugins/terminal)   |     │  协议(内存/本地socket)      |
        │ HTTP/SSE          |     ▼                         |
        └──────────────►    |   [In-process PTY 后端]  ←替换 daemon spawn
                            |     └─ node-pty (libpty_node.so)
                            └───────────────────────────────┘
        nativeLibraryDir: libnode.so + libpty_node.so        (只读，本进程加载)
```

- **不改官方 UI**：终端面板就是官方 Web UI 的原样；我们只让它的后端（`PersistentPty`）在 Android 上可用。
- **替换点**：把 `core/src/persistent-pty/daemon.ts` 的「spawn 外部 ELF + socket 协议」替换为**进程内后端**，对外仍满足
  `DaemonTransport`（`request / requestIfRunning / supports / shutdown / handoff / subscribe`）这一服务契约。
- **phase 语义**：官方对能力缺失本就有优雅降级（`supports("rename")`、`capabilities.persistentPty !== false`），
  Phase B 即利用这一契约只实现最小子集。

## 5. Phase 0 · Spike（先证可用性；Web 终端先禁用）

**目标**：在**不改架构**、不进入重量级实现的前提下，用最小改动证明三条硬前提，全部成立才进入 Phase B。

| # | Spike 验证项 | 判据（可证伪） | 落地 |
|---|---|---|---|
| S1 | `libpty_node.so` 能在**进程内 Node**（`node::Start`，`node-bridge`）`require` 加载 | `require(<nativeLibraryDir>/libpty_node.so)` 成功，`typeof spawn === "function"`；`Object.getOwnPropertyNames` 出现 `fork/spawn/open` | 一次性 host 侧 Node 脚本 + 模拟器探针 |
| S2 | `node-pty.spawn("/system/bin/sh", …)` 能起真 PTY | 取得 `pid`；`write("echo hi\n")` 后 `onData` 收到回显；`resize` 不抛错 | 同上，交互回环 |
| S3 | 交互 TUI / 作业控制生效（真 PTY 的烙印） | 起 `sh -c 'read x; echo got:$x'`，注入输入并被消费；`kill`/`SIGTERM` 语义生效 | 探针脚本 |
| S4 | 绑定加载方式选型 | 评估「① `System.loadLibrary("pty_node")` 预载 + JS 覆盖 addon 路径」vs「② Node 侧直接 `require(.so)`」哪个在 arm64 真机/模拟器最稳 | 结论落 lock 式记录 |

**Phase 0 期间 Web 终端先禁用**：在 Spike 未过之前，不让 PersistentPty 进入「可用」态，避免对用户宣称不实能力。
具体：Spike 阶段不触碰上游 `available`/`capabilities`，终端按钮默认不可用（维持现状 ❌），直到 Phase B 后端落地并经行验证。

**Phase 0 产出**：一份 `logs/PTY_SPIKE.md` + 探针证据（facts.json / probe 输出 / 截图），并冻结「加载方式选型」结论。

## 6. Phase B · 首个里程碑（Node 26.13.0 + 进程内 PersistentPty 最小后端）

### 6.1 引擎升级（Node 24 → 26）

| 面 | 现状 | 改到 |
|---|---|---|
| `gradle/libs.versions.toml` | `nodeRuntime = "24.22.1"` | `26.13.0`（新增 `nodePty = "26.13.0"`） |
| `app/build.gradle.kts` | `runtimeOnly(node.runtime)` | `runtimeOnly(node.runtime)` + `runtimeOnly(node.pty)` —— **必须同版本** |
| `runtime.lock.json` | `node 24.22.1` + SHA | 更新 `26.13.0` + `libnodeSha256`/`libcxxSharedSha256`，并登记 `node-pty` 条目 |
| `scripts/build-opencode.mjs` | 强制 `OPENCODE_NODE_TARGET=node24` | 支持/改为 **node26**（否则与设备引擎错位） |
| `scripts/smoke-node24.mjs` | Node 24 host 门禁 | 增加/改名 **smoke-node26**（--version/serve/health/UI/title/SSE 同口径） |
| `scripts/regression.mjs` | 引用 `smoke-node24` | 同步引用新 smoke |
| `scripts/verify-runtime.mjs` | 仅断言 `node-runtime` AAR | 扩展：断言 `node-pty` AAR 存在且 `libpty_node.so` SHA 锁值（新增 lock 段） |

> 引擎升级是**独立风险**（见 §9 R2）；若 26 出现阻塞性回归，退路是 **24.22.1 这对**（`node-pty:24.22.1` 已在 Central，无需升 Node）。

### 6.2 进程内 PersistentPty 后端（核心）

**设计原则**：不改 UI、不改服务层路由；只替换 `PersistentPty` 的传输/执行后端。

1. **后端宿主**：不在额外 `app_node` 层重写整个 `index.ts`（那是大工程），而是**最小替换 `makeDaemonTransport`**：
   用「进程内会话管理器」实现 `DaemonTransport` 的契约，会话直接由 `node-pty` 驱动，无 socket 往返。
2. **接线（node-pty 绑定）**：两种选型（Phase 0 S4 冻结其一）：
   - **A（推荐）** 宿主预载：`HostCapabilities` 里 `System.loadLibrary("pty_node")`（桥已负责 `libnode.so`），Node 侧
     把 node-pty 的 addon 解析覆盖到 `/…/nativeLibraryDir/libpty_node.so`；
   - **B** Node 侧直接 `require(<nativeLibraryDir>/libpty_node.so)`（Node 对 `.so` 绝对路径可 dlopen）。
   提供一个**极薄 JS wrapper**（不重实现 node-pty，只在它外面包成 opencode 需要的 `Proc`/`spawn` 接口，复用官方 `pty.node.ts` 的包装形态）。
3. **`resolveBinary` 指向内嵌入口**：让 `#persistent-pty-binary` 在 Android 形态下解析到一个**内嵌 in-process daemon 入口**
   （返回一个「已就绪」标记，而非可 spawn 的 ELF 路径），从而跳过 `spawnDaemon` 外部进程逻辑。
4. **受支持能力（Phase B 最小子集）**：

| op | Phase B | Phase A |
|---|---|---|
| list / get / create | ✅ | ✅ |
| write / resize / input / terminate | ✅ | ✅ |
| subscribe（输出流 + exit） | ✅ | ✅ |
| control / rename | rename 按能力降级（`supports("rename")=false`） | ✅ |
| snapshot / read_rows / 光标 | read_rows 降级由 live 高度近似；snapshot ⬜ | ✅ |
| 跨重启 handoff / checkpoint 回放 | ⬜（不宣称）| ✅ |

5. **session 归属 / 输出重放**：进程内缓冲 + 订阅者游标（对齐官方 `AttachInput.replay/cursor/activate/detach` 语义）；
   不引入 `@lydell/node-pty` 之外的依赖。

### 6.3 载荷与物化

- node-pty **JS wrapper 物化**：随 `collect-opencode.mjs` / 新 collect 步骤打入载荷（`config/opencode/plugin/` 或
  `<HOME>/node_modules/` 形态，平台禁 symlink ⇒ copy，遵循既有「插件物化」纪律）；
- `OPENCODE_NODE_PTY_PATH` 或自建后端 require 路径由 `payload/lib/env.js` 注入（镜像 `OpencodeRuntime.buildEnv`，双处一致纪律）。

### 6.4 Phase B 验收判据（摘要）

| 判据 | 通道 |
|---|---|
| 终端按钮进入可用态（`capabilities.persistentPty !== false`）| Web UI 截图（WebView 内容不进 uiautomator 树 ⇒ 截图/HTTP 取证）|
| 在终端内 `sh` 交互：输入回显、`ls`/`pwd`、`echo` 输出正确 | 终端面板读写 + 截图 |
| 交互 TUI（如 `top`/`vi` 或 `od` 控制码流）可渲染 | 截图比对 |
| `ctrl`/resize（列×行）触发 `resize` 生效 | 面板拖拽/旋转 + logcat |
| 无外部 ELF spawn（`spawn` 硬约束仍满足）| logcat + 反证：PATH 上无 `opencode-pty` 也工作 |
| 回归四件套全绿（在 Node 26 口径下）| `scripts/regression.mjs` |

## 7. Phase A · 全功能递进（对齐全功能终端）

在 Phase B 稳定后，按需补全：

1. **snapshot / checkpoint 回放**：对齐桌面终端「重连后屏幕恢复、光标正确」；
2. **read_rows + 光标坐标**：让「带屏文本 + 光标」语义与官方一致；
3. **跨重启 handoff**：复用 `OPENCODE_NODE_PTY_PATH` 钩子（§2.3），把进程内 `Pty` 与 `PersistentPty` 的能力复用/对齐；
4. **rename / control / 多 attachment 角色（controller/observer）**。

Phase A 每项都有独立验收判据与证据记录，不一次性铺开。

## 9. 风险与对策

| # | 风险 | 等级 | 对策 / 判据 |
|---|---|---|---|
| R1 | `libpty_node.so` 在进程内 Node 加载失败（ABI/SELinux/nativeLibraryDir 只读） | 高 | Phase 0 S1 先证；不通过则不进入 Phase B，方案如实降级 |

| R6 | `node-pty` JS wrapper 与 AAR 二进制版本漂移 | 中 | wrapper 随 `collect` 物化并 digest 幂等；`pty.lock` 配对纪律 |

### 12.2 真机白屏/断连——5 个根因（systematic-debugging + CDP 取证）

| 1 | node-pty `fork` 传 `uid/gid=0` ⇒ 非 root `setgid(0)` EPERM ⇒ pty.cc `_exit(1)`，shell 从未 exec | `fork(..., -1, -1, ...)` |
